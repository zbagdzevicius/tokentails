## Known bugs fixed (section 7 rows)

Each needs its entry in `docs/BACKEND.md` (not owned by this task; text for the doc owner below).

- **Shelter GETs expose encrypted wallet keys** (`shelter.controller.ts:15-32`, new, Security). Fixed:
  `GET /shelter` and `GET /shelter/:id` select only `_id name slug description image country
  countryCode partnerStatus role publicWallet`. MANAGER and above also get `address website facebook
  twitter tiktok foundedAt`, because the CMS shelter editor loads them and writes the whole form back
  (without them a save would blank those fields). Never `wallets`, `users`, `code`, `blessing`.
- **Staking exploit: no owner filter, user-level unset** (`cat.controller.ts:138-178`, new). Fixed:
  `CatStakingService` stakes with `findOneAndUpdate({_id, owner, staked: null}, {$set: {staked}})`
  and claims with `findOneAndUpdate({_id, owner, staked: {$exists: true, $ne: null, $lte: now}},
  {$unset: {staked: 1}})` on the CAT. Another user's cat and an unowned cat are 404, an invalid id
  400, a second stake of a staked cat 409 (it used to silently restart the week). Five parallel
  claims pay once. The user document is never written with or stripped of `staked`. The response
  carries the real reward: `{success, message, tails}`; stake returns `stakedUntil`.
- **Manager can set any `shelter`** (`profile-write.dto.ts:25-37`, BACKEND.md:344). Fixed: the DTO has
  no `shelter`; any write containing it (even `''` or `null`) is 400. `POST /user/profile` no longer
  sets `shelter`. The permission half is closed by the decision #33 fix below (only ADMIN changes a role).
- **Account takeover by email-only binding without `email_verified`** (`user.service.ts:26-35`, new,
  Security). Partly fixed (the W1 rule): a doc owning the token uid resolves first; otherwise the email
  lookup refuses an unverified token with 403 `{statusCode: 403, code: 'EMAIL_UNVERIFIED', message}`
  and writes nothing. A verified token that resolves by email `$addToSet`s its uid.
  "Verified" means `email_verified === true` only (`isVerifiedToken`, `user.service.ts:35`). This is a
  deliberate, stricter departure from F5.2 step 1a and from the task text, which also trusted
  `sign_in_provider` `google.com`/`apple.com`: a Firebase user created with an unverified password for
  someone else's address can link its own Google account, and Firebase then reports
  `sign_in_provider: google.com` while the primary email stays unverified, so trusting the provider
  would bind that token to the address owner's account. Real Google and Apple identities carry
  `email_verified: true`. Open check (deferred step 6): confirm on a real Apple sign-in, including a
  private-relay `@privaterelay.appleid.com` address, that the ID token carries `email_verified: true`;
  if it does not, Apple users get 403 EMAIL_UNVERIFIED.
  New unverified sign-ups: since task 2a, `identityConfig().enforceEmailVerified` defaults to true
  (`AUTH_ENFORCE_EMAIL_VERIFIED`), so a NEW unverified password user gets 403 EMAIL_UNVERIFIED before
  any lookup and no account is created (F5.2 step 3). The shipped client has no verification UI until
  task 3a, so new password sign-ups are blocked until then (see decision #3 and deferred step 1).
  An existing doc that already owns the uid keeps resolving (`AUTH_REQUIRE_VERIFIED_EXISTING`
  defaults to false). Full F5 is 2a.
- **Live-save user throttle passes when `req.user._id` is missing** (`live-game-throttle.guard.ts:17-19`,
  new). Fixed: fails closed with 401. The F6 per-IP throttle and replay queue part is not this task.
- **Unleased crons run on every replica** (`cat.controller.ts:64`, `user.controller.ts:282-304`, new).
  Fixed: `saveLinkedArticlesCount` (cat), `resetCheckIn`, `saveLinkedArticlesCount` (user) and
  `giveWeeklyTopRewards` run through `runLeased` (jobs `cat-status-reset`, `user-check-in-reset`,
  `user-status-reset`, `weekly-top-rewards`, 1 h lease). `giveWeeklyTopRewards` paid the top 200 once
  per replica before. The cat reset was also not awaited; it is now.
- **Shelter crash on a missing `rozine-pedute` key** (G13, backend half). `GET /cat/sale` always returns
  `tokentails`, `token-tails`, `token-tails-2`, `rozine-pedute` as arrays and keeps every shelter-slug
  key it returned before (key superset, `unknown` included). The client half (`parseStorefront`,
  non-mutating sample, `useStorefront`) is G13 client work.
- **`GET /cat/sale` dropped whole shelters** (regression in this task's first version, found in review).
  One global `.sort({_id:-1}).limit(200)` over all shelters returned 188 `rozine-pedute` cats and
  pushed older shelters out: on the dev data `token-tails` had 10 of 62 cats, `token-tails-2` 0 of 2,
  `home` 2 of 4, `unknown` was missing. Fixed: ids are grouped per shelter (`$sort` → `$group` →
  `$slice` 200, ids only), then the whitelisted cats for those ids are loaded and populated, with a
  global safety cap of 1000. Verified live on :3005: `token-tails` 62, `token-tails-2` 2,
  `rozine-pedute` 200, `home` 4, `unknown` 1, ~400 KB.
- **Manager can take over any account or grant ADMIN** (`user.controller.ts` `PUT /user/profile/:id`,
  `profile-write.dto.ts`; existing, made worse by W1-HF (d), Security, decision #33). A manager could

Mentioned, not fixed: `BaseRepository.findOne` strips `undefined` from the filter, so `{_id: undefined}`

## API changes

- Every route that used `AuthGuard('appauth')` now uses `AppAuthGuard` (71 uses, 12 controllers).
  Identical for registered users. Differences: a strategy `HttpException` (403 EMAIL_UNVERIFIED, or a
  future 409) reaches the client unchanged instead of 401; `req.user.isGuest` without `@AllowGuest` is
  403 `GUEST_FORBIDDEN`; `req.user.transient` without `{transient: true}` is 428
  `GUEST_SESSION_REQUIRED`. No guest users exist until task 2a, so nothing changes for today's traffic.
- Guest allow-list (`src/common/guards/guest-allow-list.ts`, decision #9): `GET /user/profile`
  (transient), `POST /user/catbassadors/live`, `PUT /cat/:id` (feed), and the read-only previews
  `GET /user/cats`, `GET /user/airdrop/progression`, `GET /user/leaderboard/position`,
  `GET /user/leaderboard/catnip/position`, `GET /user/leaderboard/paw-match/:level/position`.
  "Previews" is interpreted as read-only views of the guest's own progress that write nothing
  (`GET /user/codex` writes, so it is closed). A guest feed marks the cat fed but credits no Tails.
- `GET /cat/stake/:id`: 404 for a cat that is not the caller's, 409 when already staked, 400 for an
  invalid id; body adds `stakedUntil`.
- `GET /cat/stake-reward/:id`: 404 for a cat that is not the caller's; body adds `tails` (0 while the
  period runs). Shipped clients (`CatsModal.tsx:747` still adds a hardcoded +1) keep working; the
  client should read `tails` (G5 P1 client part).
- `GET /cat/sale`: required keys always arrays, whitelisted fields (never `owner`, `code`, `staked`,
  blessing `creator`), at most 200 blessed cats per shelter (newest first) and 1000 overall, a 45 s
  single-flight in-process cache invalidated by every adoption (`CatService.addCatToTheOwner`), and
  additive `_meta: {_v: 1, generatedAt, shelters: [{slug, name}]}` with one entry per shelter key in
  the response (not `tokentails` or `unknown`; a required key with no shelter document is omitted).
  `role` is added by task 2b. Until then the shared parser (`parseStorefrontDetailed`) drops every
  entry without a valid `role`, so new clients see `meta.shelters: []`; old clients ignore `_meta`.
  `STOREFRONT_REQUIRED_KEYS` and `STOREFRONT_META_VERSION` are imported from
  `src/shared-contracts/storefront` (no local copy). Shelter slugs `tokentails`, `_meta`, `__proto__`,
  `constructor` and `prototype` never become keys.
- Boards exclude guests: `GET /user/leaderboard`, `/leaderboard/catnip`, `/leaderboard/paw-match/:level`,
  `/catbassadors/leaderboard`, every `.../position` count, the weekly top-200 reward and the one-off
  `giveTails` grant filter `isGuest: {$ne: true}`. `POST /user/catbassadors/live` still saves a
  guest's scores (the F5.2 merge keeps them), which is why the filter sits on the boards.
- `PUT /user/profile/:id`: 403 for a non-ADMIN changing `email` or `permission`. `POST /user/profile`:
  403 for a non-ADMIN setting a role above USER.
- `GET /shelter`, `GET /shelter/:id`: whitelist projection as above.
- `POST /user/profile`, `PUT /user/profile/:id`: `shelter` is rejected (400).
- Auth: 403 `{code: 'EMAIL_UNVERIFIED'}` for an unverified token on an account that does not own its uid.

No new environment variables.

## Schema and index

- `User.firebaseUids: string[]` (`default: undefined`, so legacy docs stay without the field) with a
  NON-unique multikey index `{firebaseUids: 1}`. Mongoose builds it on startup. It becomes unique
  (partial on `$exists`) after the uid backfill and the duplicate-user audit (F5.3, task 2a).
- `jobruns` gets lease documents `{_id: jobName, lockedUntil, lockedAt, lockedBy, status, finishedAt}`
  next to the existing `codex-reset` document. `codex-reset` keeps its period claim, now through the
  shared `claimJobPeriod`; its behaviour and specs are unchanged.
- `User.isGuest?: boolean`, declared with no default and no index. It is needed now because Mongoose 6
  strictQuery strips undeclared filter paths from `countDocuments`/`find`, which would silently turn
  the board filter into a no-op (checked in `guest-boards.hotfix.spec.ts`). Task 2a adds the explicit
  `false` default, the backfill and the partial `isGuest:false` board indexes (F5.1).

- Storefront cap (decided in review, departs from the spec's "limit 200"): at most 200 blessed cats
  PER SHELTER, newest first, and at most 1000 blessed cats overall (`STOREFRONT_PER_SHELTER_LIMIT`,
  `STOREFRONT_LIMIT` in `src/cat/storefront.ts`), plus the 10 sampled blueprints. A single global 200
  dropped whole shelters (see the regression above); 200 per shelter instead of the reviewer's ~50
  because `MarketplaceItems` and `CatsInNeed` list every `rozine-pedute` cat. Kept as is after the
  second review: step 1 of `blessedForSale` `$push`es every unowned blessed cat id of a shelter before
  `$slice`. That is 12 bytes per id, so the 16 MB group limit is about a million unsold cats in ONE
  shelter (today: 188 in the largest), and the call runs at most once per 45 s per instance behind the
  single-flight cache. `$topN` (MongoDB 5.2+) would bound it, but the production MongoDB version is not
  confirmed here and an unsupported accumulator would turn `GET /cat/sale` into a 500, which is the
  crash this hotfix removes. Follow-up once the version is confirmed: replace `$push`+`$slice` with
  `{$topN: {n: 200, sortBy: {_id: -1}, output: '$_id'}}`.
- Founder decision #F-1b-1 (open, not covered by #35): pre-hotfix stakes pay once more. See "Founder
  decision needed" below; recommendation B, conditional on the audit count.
- Guests on boards: filter the board queries (reviewer's option b), not drop the board fields in
  `/live` (option a), because the plan keeps guest scores through the merge (F5.2) and reads boards
  through `isGuest:false` indexes.
